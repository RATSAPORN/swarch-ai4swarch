# ADR-0002: ใช้เหตุการณ์เพื่อกระจายงานหลังสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-24
- **Deciders:** ยังไม่ระบุ ต้องยืนยันผู้มีอำนาจตัดสินใจ

## Context and problem

หลักฐานสำหรับร่างนี้มีเพียง R-12 จากข้อความผู้ใช้ และแม่แบบ docs/adr/template.md ไม่มีไฟล์บริบทระบบ (context: none)

| ข้อเท็จจริง | หลักฐาน |
|---|---|
| ต้องส่งอีเมลยืนยันผ่าน MailFast แทน mock logic ของ emailservice | R-12 ข้อ 1 จากข้อความผู้ใช้ |
| ต้องให้คะแนนสะสมผ่าน loyaltyservice ซึ่งยังต้องสร้าง | R-12 ข้อ 2 จากข้อความผู้ใช้ |
| ต้องบันทึกเหตุการณ์ “order placed” ให้ทีมการตลาด | R-12 ข้อ 3 จากข้อความผู้ใช้ |
| คาดว่าจะเพิ่ม SMS, fraud scoring และการปรับ recommendations ในปีหน้า | ย่อหน้าสุดท้ายของ R-12 จากข้อความผู้ใช้ |

โครงสร้างการเรียกบริการปัจจุบัน จุดยืนยันคำสั่งซื้อ ฐานข้อมูล โปรโตคอล และความสามารถของ MailFast: Not evidenced in the provided files. ชื่อบริการข้างต้นมาจาก requirement ไม่ใช่การตรวจโค้ด

ต้องเลือกรูปแบบประสานงานที่รองรับงานทั้งสามและการเพิ่มงานในอนาคต รายละเอียดสถาปัตยกรรมด้านล่างเป็นข้อเสนอใหม่ ไม่ใช่โครงสร้างที่ตรวจพบในระบบ

## Decision drivers

ลำดับต่อไปนี้เป็นการจัดลำดับที่เสนอ ยังต้องยืนยันกับผู้เกี่ยวข้อง

- ความสามารถในการปรับเปลี่ยน: เพิ่มงานหลังสั่งซื้อโดยลดการแก้ส่วนสั่งซื้อ ตามงานอนาคตใน R-12
- ความถูกต้องและความน่าเชื่อถือ: ป้องกันงานสูญหายและผลข้างเคียงซ้ำ โดยเฉพาะคะแนนสะสม
- ความพร้อมใช้งานและ performance: [Inferred] ควรแยกความล่าช้าหรือความล้มเหลวของบริการภายนอกจากการรับคำสั่งซื้อ แต่ R-12 ไม่ระบุเวลาที่งานต้องเสร็จ
- ต้นทุนและความง่ายในการดูแล: พิจารณาภาระของ broker, retry และการติดตามงาน โดยยังไม่มีงบประมาณหรือข้อมูลทักษะทีม

## Considered options

1. ให้ส่วนสั่งซื้อเรียกงานอีเมล คะแนนสะสม และ analytics โดยตรงแบบ synchronous
2. ส่งงานให้ตัวประสานงานเบื้องหลังที่เก็บสถานะและเรียกแต่ละงาน
3. เผยแพร่เหตุการณ์ผ่าน message broker ที่เก็บข้อความถาวร ให้ผู้รับแต่ละงานประมวลผลแยกกัน

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 — เรียกโดยตรง | โครงสร้างเริ่มต้นน้อย รับผลจากแต่ละการเรียกได้ทันที | เวลาตอบกลับผูกกับงานที่เรียก เพิ่มงานต้องแก้ส่วนสั่งซื้อ และยังต้องจัดการกรณีสำเร็จเพียงบางงาน |
| 2 — ตัวประสานงานเบื้องหลัง | รวมสถานะและ retry ไว้จุดเดียว ไม่ต้องรอทุกงานในคำขอสั่งซื้อ | เพิ่มงานต้องแก้ตัวประสานงาน ต้องดูแลที่เก็บสถานะและการกู้คืน และมีศูนย์กลางที่รู้จักทุกขั้นตอน |
| 3 — กระจายเหตุการณ์ | เพิ่มผู้รับโดยไม่เพิ่มการเรียกจากส่วนสั่งซื้อ แยก retry และการขยายขนาดแต่ละงานได้ | เพิ่มภาระ broker และ event contract ผลลัพธ์เกิดภายหลัง ต้องจัดการข้อความซ้ำ การสูญหาย และการติดตามข้ามผู้รับ |

## Decision

เสนอเลือกทางเลือก 3 เพราะรองรับการเพิ่มงานที่ R-12 ระบุ โดยแยกผู้ผลิตเหตุการณ์จากผู้รับแต่ละงาน การเลือกนี้ขึ้นกับการยอมรับว่าผลงานเกิดภายหลังการสั่งซื้อได้ หากทุกงานต้องเสร็จก่อนตอบรับคำสั่งซื้อ ต้องทบทวนการตัดสินใจ

- ให้ส่วนที่ยืนยันคำสั่งซื้อสร้างเหตุการณ์ OrderPlaced หลังยืนยันสำเร็จเท่านั้น ตำแหน่งในโค้ดยังต้องตรวจสอบ
- ใช้การกระจายให้ผู้รับทุกประเภท แต่ละประเภทมี subscription หรือคิวถาวรของตนเอง เพื่อให้อีเมล คะแนนสะสม และ analytics ต่างได้รับเหตุการณ์
- ปรับ emailservice ให้รับเหตุการณ์และส่งอีเมลผ่าน MailFast แทน mock logic; ให้ loyaltyservice รับเหตุการณ์เพื่อให้คะแนน; เพิ่มผู้รับสำหรับบันทึก analytics โดยยังไม่เลือกผลิตภัณฑ์หรือที่เก็บข้อมูล
- กำหนด event contract ที่มี event_id, order_id, เวลายืนยัน และเวอร์ชัน schema ข้อมูลสำหรับส่งอีเมลและคำนวณคะแนนต้องตกลงเพิ่ม จำกัดข้อมูลส่วนบุคคลตามความจำเป็นของแต่ละงาน
- รองรับการส่งอย่างน้อยหนึ่งครั้ง ผู้รับต้องเก็บสถานะและป้องกันผลซ้ำด้วยกุญแจของคำสั่งซื้อและประเภทงาน โดยการเพิ่มคะแนนกับบันทึกว่าทำแล้วต้องเป็นอะตอม
- ต้องกู้เหตุการณ์ได้เมื่อยืนยันคำสั่งซื้อแล้วเผยแพร่ไม่สำเร็จ เสนอ transactional outbox หากที่เก็บคำสั่งซื้อรองรับ transaction เดียวกัน มิฉะนั้นต้องออกแบบวิธีกู้คืนและพิสูจน์ว่าไม่ทำงานหายก่อนใช้จริง
- แยก retry ที่มี backoff และขีดจำกัดต่อประเภทงาน มีพื้นที่เก็บงานที่ล้มเหลวถาวร การแจ้งเตือน และการนำกลับมาประมวลผล ค่าเวลาหรือจำนวนครั้งยังไม่กำหนด
- เสนอนโยบายให้งานที่สำเร็จแล้วคงผลไว้เมื่ออีกงานล้มเหลว และเก็บงานที่ล้มเหลวไว้กู้คืน นโยบายนี้ยังต้องยืนยัน

ยังไม่เลือก broker, SDK หรือโปรโตคอลของ MailFast เพราะไม่มีหลักฐานประกอบ

## Consequences

- **Positive:** เพิ่ม SMS หรือผู้รับอื่นด้วย subscription ใหม่ได้เมื่อ event contract เพียงพอ (คุณลักษณะคุณภาพ: ความสามารถในการปรับเปลี่ยน)
- **Positive:** retry แยกแต่ละงานได้ และรองรับ MailFast ขัดข้องชั่วคราวภายใต้ความจุและระยะเก็บข้อความที่ต้องกำหนด (คุณลักษณะคุณภาพ: ความพร้อมใช้งานและความน่าเชื่อถือ)
- **Negative:** อีเมล คะแนน และ analytics อาจยังไม่เสร็จเมื่อตอบรับคำสั่งซื้อ ต้องตกลงเวลาที่รับได้และการแสดงสถานะ (คุณลักษณะคุณภาพ: performance และความสามารถในการใช้งาน)
- **Negative:** ต้องดูแล broker, สถานะผู้รับ, schema และการติดตามเพิ่ม (คุณลักษณะคุณภาพ: ต้นทุนและความสามารถในการดูแลรักษา)
- **Risks and mitigations:** เหตุการณ์อาจหายระหว่างยืนยันและเผยแพร่ ใช้ outbox หรือวิธีกู้คืนที่ผ่านการทดสอบ (คุณลักษณะคุณภาพ: ความน่าเชื่อถือ)
- **Risks and mitigations:** การ crash หลังส่งอีเมลแต่ก่อนบันทึกสำเร็จอาจทำให้ส่งซ้ำ ใช้ idempotency ของ MailFast หากรองรับ และกำหนดวิธีตรวจสอบผลคลุมเครือหากไม่รองรับ ไม่รับประกันผลแบบ exactly-once จาก broker เพียงอย่างเดียว (คุณลักษณะคุณภาพ: ความถูกต้อง)
- **Risks and mitigations:** ข้อมูลลูกค้าอาจกระจายเกินจำเป็น จำกัด payload, สิทธิ์เข้าถึง และระยะเก็บตามนโยบายที่ต้องยืนยัน (คุณลักษณะคุณภาพ: ความปลอดภัยและความเป็นส่วนตัว)

## Validation

รายการต่อไปนี้เป็นแผนตรวจสอบ ยังไม่ได้ดำเนินการ

- ทดสอบคำสั่งซื้อสำเร็จหนึ่งรายการว่าเกิดอีเมลผ่าน MailFast คะแนน และ analytics ครบ; คำสั่งซื้อที่ยืนยันไม่สำเร็จต้องไม่กระตุ้นงานเหล่านี้
- ส่งเหตุการณ์เดิมซ้ำและจำลอง crash ระหว่างทำงาน ตรวจว่าคะแนนและ analytics ไม่ซ้ำ และตรวจผลอีเมลตามข้อตกลงกับ MailFast
- จำลองล่มหลังยืนยันคำสั่งซื้อแต่ก่อนเผยแพร่ ตรวจว่ากู้เหตุการณ์และทำงานครบได้
- จำลอง MailFast ใช้งานไม่ได้ ตรวจว่างานคะแนนและ analytics เดินต่อได้ และงานอีเมลกู้คืนได้เมื่อบริการกลับมา
- ทดลองเพิ่มผู้รับ SMS เพื่อตรวจว่าต้องแก้ส่วนสั่งซื้อหรือไม่ และตรวจความเข้ากันได้เมื่อเปลี่ยน schema
- วัดเวลาจากยืนยันถึงแต่ละงานสำเร็จ อายุงานค้าง จำนวน retry และงานล้มเหลวถาวร กำหนดเกณฑ์ผ่านหลังตกลงเป้าหมายและปริมาณงาน

## Open questions

- ใครเป็นผู้ตัดสินใจ และลำดับความสำคัญที่เสนอถูกต้องหรือไม่?
- “สั่งซื้อสำเร็จ” หมายถึงจุดใด แต่ละงานต้องเสร็จภายในเวลาเท่าใด และยอมรับการทำงานภายหลังกับนโยบายไม่ย้อนกลับได้หรือไม่?
- ระบบเก็บคำสั่งซื้ออย่างไร และรองรับ outbox หรือกลไกกู้คืนใดได้?
- ปริมาณคำสั่งซื้อ ภาระสูงสุด งบประมาณ ทักษะทีม และข้อจำกัดโครงสร้างพื้นฐานเป็นอย่างไร?
- MailFast มี API, authentication, rate limit, sandbox และกลไก idempotency หรือตรวจสถานะใดบ้าง?
- สูตรคะแนน ข้อมูลระบุตัวสมาชิก และนโยบายยกเลิกหรือคืนสินค้าคืออะไร?
- การตลาดต้องการ schema และปลายทาง analytics ใด? ต้องการลำดับเหตุการณ์ การกำจัดเหตุการณ์ซ้ำ และระยะเก็บข้อมูลแบบใด?
- ใครดูแลงานค้าง การแจ้งเตือน และ replay? ต้องตั้ง timeout, retry และระยะเก็บข้อความเท่าใด?
- fraud scoring ในอนาคตเป็นงานหลังสั่งซื้อหรือเงื่อนไขก่อนยืนยัน? หากเป็นเงื่อนไขก่อนยืนยัน ต้องออกแบบเส้นทางนั้นเพิ่มเติม
